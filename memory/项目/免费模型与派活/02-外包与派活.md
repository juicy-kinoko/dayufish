# 外包与派活 —— 省 token 的活怎么甩出去

> 概述：外包纪律 + 派活方法。**具体通道参数在 `03-员工池.md`，方法详解在技能 `~/.dsh/skills/worker-team/SKILL.md`。** 本页只记决策。
> 旧版通道清单已归档 `_archive/20261107/`。

---

## 零、一句话原则

**能一行 python 说清的活，绝不自己长篇推理。**
我的 token 花在判断、决策、写文件、调工具，不花在翻译、摘要、分类、抽取。

## 一、先算账：值不值得派

派活有成本——**我写 prompt 也要花 token**。

| 判断 | 结论 |
|---|---|
| 单块 < 300 字，且只有 1 块 | **自己干**，省不下还多一轮验收 |
| 3 块以上同构的活 | **派**，边际成本趋零 |
| 单块 > 800 字长篇 | **派** |
| 要读当前对话 / 调工具 / 动文件 | **自己干**，员工看不见这些 |
| 错一个字就废（配置、密钥、命令） | **自己干**，或派完逐字核 |

判断标准：**我能不能写出一段自包含的 prompt，把员工需要的全部事实都塞进去？** 能就派。

## 二、分型派活（`-p`，别用一条链从头撞）

| 分型 | 首选链 | 用途 |
|---|---|---|
| fast | conatus → flint → kilo → dots | 短输出、打标、改写 |
| long | flint → conatus → nemotron | 长文、摘要 |
| code | flint → glm → kilo-code | 代码、结构化格式 |
| think | glm → flint → kilo | 推理分析 |
| bulk | conatus → flint → kilo → dots | 大批量 |
| safe | glm → flint → conatus | 格式严、错就废 |
| cheap | kilo → kilo-code → dots | 纯机械活，越快越省 |

`long`/`code`/`think`/`safe` 带 **cap ≥ 80 门槛**，弱员工接不到难活。

**我指定过顺序就尊重我的顺序**，只把刚翻车的挪后；没指定才按优先级 + 战绩自动排。

## 三、先干跑再花钱

```bash
team.py tasks.json -p fast --plan    # 不发请求，只出方案、预算、耗时
```

方案不对就改，**别拿真请求试错**。

## 四、任务怎么写

```json
{"name":"01-渠道说明","prompt":"…事实给全…\n第1行：渠道名：…",
 "must_start":["渠道名：","适合："],"profile":"safe","max_tokens":500}
```

1. **`must_start` 是格式锚点**，缺一个就判不合格自动重做——最便宜的质检。
2. **事实必须给全**，员工没有背景知识也不会去查，会编。
3. **`max_tokens` 按需给**，推理型给少了交白卷（脚本会自动加倍，那是浪费）。
4. **一次一个活**，塞三件事三件都半吊子。

## 五、质量四级阶梯

```
① 一次过  → 交
② 不合格 → 自动换人重做 → 交，记一次回收
③ 换不到 → 我自己改 → 交，标明"改过"
④ 改不动 → 自己写 → 交，标明"自写"
```

**绝不用不合格稿凑数。** 脚本退出码 1 就是有活没交上。

## 六、调用姿势

**❌ 不要用 `http_request`** —— 响应头几百行倒进对话，噪音比省下的还贵。
**✅ 用脚本 + urllib，只 print 正文**。现成的：

```bash
llm "问题"                      # 单发，自动换道
team.py tasks.json -c 3         # 批量，见技能
team.py --stats                 # 看战绩与净省
```

## 七、踩过的坑

1. `max_tokens` 太小 → reasoning 吃光 → content 空（推理型必踩，给 512~1024 或让脚本自动加倍）
2. 免费档突然 401/429 = 活动结束或限流，**换通道，不是配置坏了**
3. 员工答案别原样交付，尤其命令、配置、数值、模型 ID —— **它们会一本正经地编**
4. 并发别一把梭，按 `concurrent` 走；撞 429 先等 2s/4s 重试，别急着换人

## 七·五、留证据：成功失败都存快照（老大 2026-11-07 定）

**光记成败不够，得能回头看"它当时到底写了什么"。**

| 存哪 | 存什么 |
|---|---|
| `logs/runs.jsonl` | 每任务一行账本：通道、成败、失败原因、耗时、prompt（截 400 字）、产出前 160 字、md5 |
| `logs/snap/<批次>/<任务>.out.md` | 产出全文 |
| `logs/snap/<批次>/<任务>.fail.md` | 任务 prompt + 每个员工错在哪 + **它吐出来的样本** |
| `logs/snap/<批次>/_config.json` | 这一批的全部参数（否则事后不知道是哪个配置跑的数据） |

```bash
team.py --snap        # 看最近一批
team.py --stats       # 胜率、净省、距分析门槛还差多少
```

**快照不怕大，别随手删**——那是复盘质量的唯一凭据。整批清之前先确认账本还在。

## 八、迭代节奏（老大 2026-11-07 定）

- **攒够 100 个真实任务**才回看 `--stats`（它会显示还差多少），小样本不改配置。
- 改完跑 `team.py --mark` 记账。
- 重考只在池子变动或某员工连续翻车时做，一次只考一个。
- 调整顺序：先 `_profiles`（派给谁）→ 再 `concurrent`/`gap`（怎么并）→ 最后 `cap`（行不行）。

## 十、挂机跑一整天（2026-11-08 晚新增）

老大要求：大任务挂整天，**中途失败自动重试，不许让人手点**。

- 入口：`bin/longrun.py tasks.json -o 产出目录 --hours 24`
  - 每轮调 team.py 补没交稿的；FAIL 不落盘，下轮自动再投；两轮之间歇 5s→×1.5→封顶 600s
  - `--budget` 单任务兜底分钟（0=不限）；`-b`/`-c`/`--max-c` 透传 team.py
  - 跑满 --hours 才停；断了重跑同一条命令接着补（已交稿的 SKIP）
- 防卡死三道保险（实测验证过）：
  1. `call_guarded` 看门狗：每次请求独立线程，任务级 deadline（min(兜底,15分钟)）到点强杀继续走
  2. `HARD_CALL_CAP=420s`：单次 HTTP 硬上限，urllib 赖着不回就掐
  3. longrun 轮级 `timeout=5400`：子进程整体卡死 90 分钟掐了重开
- 实测：flint 连吃 429 两轮，longrun 一声不吭自动重试，零人工介入。
- 挂后台命令：`nohup python3 ~/.dsh/skills/worker-team/bin/longrun.py ... >> logs/longrun.out 2>&1 &`；看进展 `tail logs/longrun.log`
