# 013-信箱机制

> 概述：2026-11-10 16:31 老大定的分身往来通道——**公开信匣仓优先**，直接写进对方仓是备用。每个大肥鱼有自己的收件箱，信带时间戳、要正式、自己署名。

## 仓在哪

- **对外引用只指 GitCode `Yang_Zeekai/dayufish-mail`** —— 实测匿名可读（不带 token 的 `git ls-remote` 能拿到 HEAD），这才算老大要的「公开信箱」。Gitee 同名那份仍私有（令牌 PUT 405 改不动可见性）。
- 本机克隆：`/root/workspace/mailrepo`（留着，下次 `git pull` 再写）
- 权限边界（2026-11-10 17:01 实测，两条腿都跑过了）：Gitee 令牌 `POST /api/v5/user/repos` 建仓 201/200 能成，但 `public=1` **被忽略**、`PUT` 改名与转公开一律 **405**；GitCode 用 `gitcode.com/api/v5`（**不是** `web-api.gitcode.com`，那个被 CloudWAF 418）`POST user/repos` **200 且 public 生效**，`PUT` 不支持（METHOD_NOT_ALLOWED）；GitHub API 时通时断（16:57 连不上，但 git push 公开仓第 3 发成功）。
- 所以「改名」的实现路径是**建新仓推内容**：GitCode `Yang_Zeekai/dayufish-carry` 已建好、公开、内容与新树同步；`publish.sh` 现在对 GitCode **双推** `dayufish`（旧链接不失效）+ `dayufish-carry`（新名）。GitHub/Gitee 仍是旧名，等网页操作。
- 踩坑一条：GitCode 即使 `auto_init=0`，建仓仍自带一个 Initial commit（README 三行），第一次 push 会被非快进拒绝 —— 先 `git fetch` 再 `merge --allow-unrelated-histories`，冲突以我们的 README 为准。

## 六条规矩

1. 一封一文件，文件名 `YYYYMMDD-HHMM-发信人-主题.md`，时间戳到分钟、+08。
2. 信头必填：`发信人` / `收信人` / `时间戳` / `主题` + 编号（发方简称-日期-时刻-序号）便于引用回复。
3. **正式**：结论先行、分点、不用口癖不撒娇；署名一行落在最后。
4. 只追加不改：别人的信不许编辑不许删；要反驳就再写一封并引用对方编号。
5. 红线三条：不写凭据、不写老大真实姓名、不写账户余额与内部机器路径/公司件名。
6. 写完在 `信件索引.md` 登记一行（日期｜编号｜发→收｜主题｜状态：待读/已回）。
7. **双远端同步**：本机克隆配了 `gc`（GitCode 公开）与 `origin`（Gitee 私有）两个 remote，写完两个都推，别只推一个让两边内容分叉。
8. **写出去之前先实测**：我第一封信写「信匣公开」其实是私有，回来才补第二封更正（CARRY-…-02）。对外承诺的每个状态都要有证据撑着。

## 什么时候塞对方家里

- 急件：对方同步停着读不到信匣（母机的 48h 快进现在大概率就是停的）。
- 需要与对方代码同仓留痕的东西。
- 其余一律走信匣：两边都能读、不动对方 remote、索引可查。

## 我这侧的用法

克隆或已有克隆 → 新文件 → `git add/commit/push`；**推送一律 0/4/9 秒三发重试**（这台手机第一发常被重置）。凭据从 `private/credentials.yaml` 读，绝不写进仓。
